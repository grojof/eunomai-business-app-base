# Decisions

| Decision | Why | Rejected |
|---|---|---|
| Clone and own, not a dependency | Each organization and application is free to change anything, with nothing to stay tied to | A versioned component package: updates reach everyone, but it ties applications to the package and limits changes |
| One repository is both demo and starting point | Simple: clone it and delete one folder | A separate demo and template: two things to keep in step |
| The demo is deleted, the components stay | An application keeps no screens it does not use, and a small set of macros costs little | Copying components on demand: slower, and easy to miss one |
| Built from zero against published standards | Existing applications differ from each other, so copying them would copy the differences | Deriving the component list from existing applications |
| No Alpine.js: `app.js` is enough | The stack named Alpine in its CSP build for milestone 3, so the hardest case was tried first without it. ARIA's combobox is about 160 lines of plain JavaScript, it works by keyboard, and it falls back to a plain select. Nothing else in the forms needs behaviour in the browser: htmx does the requests and the browser's `dialog` keeps the keyboard. Alpine's CSP build runs no `eval`, so anything past a simple expression would stay in a script, the same code in another place, for one more copied file on every page and a second way to write behaviour. A screen with a lot of state in the browser may still bring it: that needs a decision here, the two-week rule, and a run in real Chrome with no policy violation | Alpine.js in its CSP build, as the stack first said |
| Pages made on the server | One language, no npm and a small supply chain; AI assistants produce reviewable code | A React client: a large npm tree, and more than most internal applications need |
| Tailwind with daisyUI, as a recommended layer | Components with free customisation: a utility overrides a component without fighting global styles. Themes are variables, and daisyUI's generator writes them. No Node: one executable, checked by hash, and the generated CSS is committed. Both are MIT; no paid part is used | Bootstrap: its look and global styles force custom classes for anything different. Writing every component by hand: all behaviour and accessibility to maintain |
| Screens call macros, not daisyUI classes | An organization can replace the CSS library in `app/ui/` without touching a screen | Classes written directly in each screen |
| Component documentation split into small pages by a script | About 375 tokens per component against 20,000 for the whole file. The official file has a regular structure, so it can be cut at its headings. Whatever code can do with certainty is not left to an assistant | Reading the whole file each time; pages written by hand |
| `llms.txt` rebuilt from the version's git tag | The site serves only the latest, so a download could not be repeated for a pinned version. The hash of the site's build file guards the recipe: if it changes, a person compares them | Downloading it from the site: its bytes change with no version to pin |
| `app/ui/catalog.py` as the one list of components | The gallery, the documentation, `catalog.json` and the search cannot disagree, and it survives deleting the demo | A list in the demo |
| daisyUI held back when its new files break `docs/components/` or the gallery | Whether a new component is good for applications is a person's decision, and it must not delay a security update elsewhere. All of daisyUI's files stay at their version, an issue says why, the rest goes ahead | Stopping the whole update |
| Tests run on pull requests, not again on `main` | Merging through a pull request with tests already passed makes a second run a repeat of about 10 minutes on each system. Nothing enforces this on a private repository without a paid plan: changes reach `main` only by pull request as a working rule. A public repository should require pull requests, passing tests and an up-to-date branch | Running them again on every push to `main` |
| A class with no CSS counts as invented | Tailwind generates only what exists, so the check covers daisyUI and Tailwind alike, for the classes it can read | Comparing with daisyUI's class lists, which would not cover Tailwind |
| What daisyUI writes inline moves to `app.js` | `style="..."` and `onclick` break the Content Security Policy. `data-style` goes through the CSSOM, which the policy allows | Weakening the policy |
| The gallery is generated from daisyUI's documentation source | 590 official examples cannot be kept by hand, and a new version must update them by itself. The source is pinned to daisyUI's version and hash-checked, and one tested function changes the examples. The pages' structure is checked by the parser, not by a hash of daisyUI's renderer: a refactor there must not hold daisyUI back, a changed page must | Specimens written by hand, which showed a fraction of each component; downloading from daisyui.com, which serves only the latest |
| `llms.txt` for assistants, the documentation source for the gallery | They have different jobs: the first is short and cut into pages to read, the second has every example with its translations | One source for both: `llms.txt` has a handful of examples, the documentation is too long to read |
| One gallery, no separate catalogue | Two lists of components disagree. Our macros appear on the pages of their components | A *Component catalogue* page beside the gallery |
| Accessibility scan as a gate on real screens, not on official examples | Examples are reference material, published by someone else, and hiding the ones that fail would hide what daisyUI offers. Available says so: it is not a promise. Screens are what people use, so they stay gated | Keeping the scan on the gallery, which decided what could be shown and left it half empty |
| Example previews fixed to their box with `contain: layout` | One rule keeps dock, FAB, toast and drawer inside, for every example, with no change to what is published. A native dialog stays in the top layer: containing it would stop it being modal | Wrappers per example, as daisyUI's site writes by hand; opening dialogs as non-modal |
| Copied code is the transformed code | It works here as it is. The published form breaks the policy, and daisyUI's site is one click away | Showing the published code, then running something else |
| The settings menu is shell, with `APP_LAYOUT_CHOICES` | An organization compares styles once and fixes one; an application may fix all of it. It follows `APP_LAYOUT_*`, and one setting both fixes and hides | A demo page, which an application would lose; one setting per option |
| daisyUI's `theme-controller` inside a form, moved to Available | daisyUI says to save its state yourself, and a form does: the class changes the theme at once, the server saves it. On its own it still saves nothing and has no *system*, so its note stays. Not Approved until a person reviews it | Our own control with the same looks, which would show less of what daisyUI offers |
| A select with a button; radios and toggles that send at once | On a closed select, arrow keys change the value: sending each would change the language under a person reading the list. A theme is a small change, undone with the same key, and focus comes back | Sending the select on change; a button on every control |
| The command palette in the shell, with options made on the server | Every application gets it, it needs no service, and what a person may open is decided where permissions are | A search service; a JSON index and templates in JavaScript |
| Examples that use Tailwind's own colours stay without them, and say so | The palette stays out of the stylesheet so that a screen cannot use it. Bringing it back for 19 examples would undo that rule | Restoring the palette in the demo |
| Native browser features for menus: `popover` and `details` | Escape, focus and outside clicks with almost no JavaScript | daisyUI's hidden-checkbox drawer, whose button cannot be reached by keyboard |
| daisyUI's `light` and `dark` themes as they come | They are designed and maintained by daisyUI, and an organization changes them with its generator. A palette of our own only added problems | A custom neutral palette, which made alerts too pale to see |
| Tailwind's own palette removed, invented values refused by a test | Colours exist only in the brand; an organization wanting more freedom removes the test. Official examples are reference material, outside the test | Trusting each author |
| Language support from the first screen | Adding it later touches every text | Single language first |
| UTC as the default time zone | The base belongs to no place; an application sets its own in `APP_TIME_ZONE` | The time zone of whoever wrote it |
| Checks over instructions | Long instructions are followed unevenly; a failing check is not | Extensive rule documents |
| `--no-proxy-headers` as a flag on the start command | Uvicorn reads it before the application loads, so no code setting can reach it. Forgetting it fails closed, with 401 for everyone, and a test checks every documented command | A start script of our own: one more file, for one flag |
| `ONLY_ON_DEMO` rows become *By hand* in a clone | Deleting the demo deletes their only proof, and *Automatic* must keep meaning a test exists | Leaving them *Automatic*, which the tracing test would refuse; keeping demo tests in every application |
| `AGENTS.md`, and skills only if a procedure needs one | The rules and procedures work with any assistant, and can be removed freely | Binding the repository to one assistant or method |
| Rules in one page, each with its official source and its check | Quality follows published standards, not an assistant's judgement, and every rule can be traced to its test. What no source requires says *Project decision* | Sources kept in skills: they load only sometimes and can be removed |
| Themes set by the server | No JavaScript: without a choice, the browser's own preference applies | A script reading the preference |
| Translations read directly from `.po` files | Nothing to compile | Compiled `.mo` files |
| Browser tests on the installed Chrome | Nothing is downloaded | Playwright's own browsers |
| Babel for formats and translations | Pure Python, one dependency for both jobs, and the usual choice for Python web applications | PyICU: closer to CLDR, but it has no ready package, must be compiled on each server, ties its version to the system, and handles no `.po` files |
| CLDR's `minimumGroupingDigits` applied through Babel's own `group_separator` | The standard says 1250 and 12.500 in Spanish, and Babel ignores that field. The values come from Unicode's data for the CLDR version Babel uses (`tools/cldr_grouping.py`), and a test fails if they part ways. Delete it if Babel adds support | A list written by hand, which was wrong for regional variants; accepting the difference, which only affects how numbers look |
| Decimal context sized to each value | Python's default of 28 digits, or any fixed limit, cuts longer values without an error | A fixed precision |
| PostgreSQL as the real database, SQLite for the demo and previews | A clone runs with nothing installed, and production gets exact numbers, real time zones and many writers. The price is two engines, and [their differences](specification.md#where-the-two-databases-differ) are written down and tested | PostgreSQL alone: the first run would need a server or a container. SQLite alone: no exact numbers and one writer. An embedded PostgreSQL: server binaries to pin for each system |
| SQLite refused in settings, and production as the default environment | It fails where `fake_identity` fails, before anything runs, and a server nobody configured stops instead of keeping its data in a file. A list of what is allowed, not of what is refused, so another driver's spelling cannot slip through. A demo deployed in production needs PostgreSQL too, even while its screens read no table | Refusing when the application starts serving: a migration or an import would already have run on the wrong database |
| Decimals on SQLite as text with a collation | The value stays readable and exact, and ordering and comparing need no change in a query, even written by hand: a table can sort by cost on both databases. The comparison runs in Python, about 0.65 seconds for 50,000 rows. An index on the column pays that when rows are written, and a page then takes under a millisecond | `REAL`: a float. Whole numbers scaled by a factor: one scale per column, and no reading the file. Padded text that sorts by itself: unreadable, and negative numbers need a complement. Refusing to order: the next table could not sort by cost on SQLite |
| Sums, functions and arithmetic refused on SQLite, in one check before each statement | SQLite turns text into a float without a word, and there is no collation for that. One place sees every statement built with SQLAlchemy, whoever wrote it. `total()` and `exact_sum()` give the same answer on both | A query helper to remember to use: the mistake is forgetting it. Replacing SQLite's `sum` on each connection: it would slow every other sum, and it cannot reach arithmetic |
| Values too long for the column refused on both databases | PostgreSQL rounds extra decimals in silence, SQLite would keep them, and an exact value must not depend on the database | Letting each one do what it does |
| One exact type for all money and quantities | One thing to learn, and no column can pick a scale that later cuts a value | A precision per column |
| The session commits in the route, not in the dependency | The end of a dependency can run after the response has left, and a failed commit must still reach the person | A commit in the dependency: quiet, and too late to report |
| Synchronous database access | One way to write a route, no extra driver for SQLite, and worker threads are enough for internal applications | The asynchronous engine: every model and query must avoid lazy loading, and SQLite would need another dependency |
| Nothing connects until a query does, and a screen on the generated rows says what to run | The first run stays `cp .env.example .env` and one command, with no database to prepare and no file left behind. Generating is one more command, which the screen shows with a copy button, so nothing has to be read first. Migrations behind the code count as missing, because the same command cures them | Migrating and generating on start: seconds of waiting on each reload, and a file nobody asked for. A button on the screen that generates: a request of seconds, before long tasks exist |
| Demo rows from a hash of the seed and the position | The same rows on any Python, which `random` promises only for `random.random()`, and a row does not depend on how many others there are. It needs nothing installed | A third-party faker: a dependency for names we already have, and its output changes between versions |
| Alembic's settings in `pyproject.toml` | One file less, and Alembic reads it since 1.16 | `alembic.ini` |
| The demo's tables in `migrations/versions/`, one file `tools/remove_demo.py` deletes | One place for migrations, and Alembic's commands need nothing explained | A second folder of migrations in `app/demo/`: a setting to change on removal, and `--version-path` to explain |
| A listener on every reflected table keeps the collation of exact columns | A batch migration on SQLite copies a table from what it reads, and SQLite reports no collation, so a downgrade left costs sorting as letters with no error. One listener covers every migration of every clone. `alembic check` cannot see this, so a test compares the file's real tables after each step | A `table_args` in each migration, which the next one would forget |
| Batch mode on both databases, with foreign keys off for each SQLite migration | A migration written against one has to run on the other. On SQLite a batch change drops a table, and with foreign keys on that would empty the tables pointing to it | Batch on SQLite alone; leaving them on |
| Windows runs by hand, not on every pull request | The application runs on Linux, in an assistant's sandbox and on servers, and Ubuntu covers SQLite and PostgreSQL. The Windows job took about 17 minutes to say nothing new on most changes. Run it before publishing, or after a change to paths or tools: `workflow_dispatch` adds it, and the Dependencies workflow starts it for each update. The matrix is built from the event, because `jobs.<id>.if` cannot read `matrix`, and one list of steps stays | Windows on every pull request; a second job, which copies the steps |
| One Ubuntu job with PostgreSQL, through a service whose image is empty on Windows | The runner skips a service with an empty image, so the matrix stays one job and one list of steps | A separate job for PostgreSQL, which repeats its setup; starting a container from a step |
| psycopg, under LGPL-3.0 | The usual driver, and the default of SQLAlchemy 2.1. It is installed as a package, neither copied into the repository nor changed. An organization that distributes an application to others should read that licence. Everything else added is MIT | psycopg2: its successor is psycopg 3. pg8000: pure Python, with a smaller user base |
| A native table, everything on the server | Only one page of rows reaches the browser, and a native table needs no keyboard code of ours. W3C's sortable table example is this: `aria-sort` and a button in the header. daisyUI gives the look only, in all cases | Tabulator: 455 KB, `role="grid"` without the `aria-rowcount` W3C asks for when rows are not in the page, keyboard focus only on editable cells, and open keyboard and screen-reader issues. An application that needs spreadsheet-like editing can still add it |
| A value outside its list is ignored, not refused | The address is something people keep. A bookmark from before a column was renamed should still open, and nothing unlisted reaches a query either way | An error page for an unknown sort or page |
| htmx keeps no history in the browser: going back reloads the address | Its copy of the page holds what the HTML said, not what a form held, so going back could show a filter that does not match the table. It would also leave rows in `localStorage`. The address already holds the state | htmx's default cache of ten pages |
| htmx settles at once, with `defaultSettleDelay` at 0 | htmx wires what arrived when it settles, 20 ms after the swap by default. Until then a new link is a plain link, so a second click on Next reloads the page and focus goes back to its top. A double click is enough. The delay exists for CSS transitions between old and new attributes, and no screen has one | htmx's default of 20 ms |
| A label sorts by what a person reads, with `case` | Sorting by the stored value puts *Almacén* last in Spanish, because it is stored as *Warehouse*, and a state has an order of its own. Positions are computed per language and bound as parameters | Sorting by the stored text; a table of labels per language |
| A list's width and density are a person's layout choices, offered on the list itself | They say how a person likes to read lists, not what a list shows, so they belong with the layout, in a cookie, and every list follows them. A toggle on the list makes them easy to find, and the settings menu holds them with the rest. The address keeps what a list shows, so a shared link does not impose someone's density. Dense uses daisyUI's `table-xs` and shows the columns that wait for a wide screen sooner; rows are about a fifth shorter, held by the row actions' 24 pixels of A11Y-06 | A `density` in the address, which a shared link would pass on; the shell's `density`, which shrinks every control and not only the rows |
| A filter panel's state in the address, with a default that depends on the screen | Open or hidden is what a page shows, so it is kept as the rest of a list's state is, and a sort link cannot open a panel a person closed. Without a state in the address the panel is beside a wide list and closed on a phone, where open it would push the rows below the screen. The button asks the server for the other state, which costs a request and keeps every link of the list right; it says what is on screen with `aria-expanded`, and without JavaScript one link per width says the same | Hiding it in the browser alone, which leaves the links of the list with the old state; a cookie, which a shared address would not carry; open everywhere, which on a phone puts the filters where the rows should be |
| The page's title in the top bar is still its `h1` | A copy in the bar and a hidden `h1` in the page would say the same thing twice to a screen reader, or once in the wrong place. The layout draws the content first, so the macro hands its title over and nothing is written twice. Top navigation fills the bar, so the title stays in the page there | A visual copy beside an `h1` hidden from sight; a block each page must fill |
| The first column pinned with a class of ours | daisyUI's `table-pin-cols` pins every `th`, so the header row piles up when the table scrolls sideways | A header of `td`, which is what makes that class work and loses the headers for a screen reader |
| Excel files read back by unzipping their XML in the tests | The file format is XML in a zip, and the standard library reads both. openpyxl would be a dependency for the tests alone | openpyxl |
| An apostrophe before text that could start a formula | A string cell is not run by Excel, but the type is lost when the sheet is saved as CSV, which is OWASP's reason. The price is a visible apostrophe on a name like *-40 C freezer* | Excel's `quotePrefix`, which hides it but protects nothing once the file is CSV |
| An export in a temporary file the system deletes, closed by the response | The file holds business data. On today's server a client that leaves does not stop the response, so a background task did run, but that rests on how `BaseHTTPMiddleware` and Uvicorn happen to behave: a failed send or a server stopping skips it, and a test proves both. A file deleted on closing leaves nothing even if the process dies | `BackgroundTask`, which runs only after a response that finished; reading the file into memory, which is simple but holds a whole list per download |
| Reading a form with small functions, not Pydantic models | Each field needs its own words in the person's language, read when the request runs, and a form must report every problem at once with what was typed intact. A reader raises one message and `read_fields` collects them. Pydantic gives English messages about types, and its errors would need mapping back to each field | A form model per screen |
| `{id:int}` limited to 19 digits for the whole application | Python refuses to read an int of more than 4,300 digits, so Starlette's convertor turned a long address into a 500. Registering the convertor once covers every route, a clone's included, and a route needs no check of its own | A check in each route, which the next route would forget |
| An error page for a form that cannot be read | FastAPI's default 422 is JSON that repeats what was sent. No page of ours sends that form, so a person gets a page | Leaving it as it is |
| Uploads checked by their first bytes, against a short list, with no new dependency | The standard library and three signatures cover what the demo takes. `python-magic` needs a system library on each server, and `filetype` is a dependency for what ten lines do. A polyglot passes either way: that is what a virus scanner is for, and the specification says so | A library for file types; trusting the extension or the type the browser sends |
| A double extension refused outright, `report.v2.pdf` with it | A list of dangerous inner extensions is a list of what someone remembered. The message says how to rename the file, which costs a person seconds. A clone can relax it in one line | Checking the inner extension against a list of dangerous ones |
| A limit on every request, read in two steps | FastAPI parses a form before dependencies run, so a role check comes too late to stop a body being written to disk. A declared length is judged before a byte is read, and every body is counted as it arrives, because a header is a promise: h11 frames by `Transfer-Encoding`, so a small `Content-Length` beside it once let 60 MB through. A request with both is refused | Reading the stream in the route: a route using the database is `def`, and it would lose FastAPI's form handling |
| Files are kept only when the whole form passes | Otherwise a failed save leaves files with no row, and a form would need a token to find its file again. The price is choosing the file again, and the form says so | Holding a refused form's file under a token, with a sweep to clear them |
| A double create without JavaScript is a known limit | With htmx the button is disabled while a form is sent. Without JavaScript nothing stops a second click from making a second work order: an edit has its version, and a new row has nothing to compare. A clone where that matters adds a one-time form token: a random value in a hidden field, recorded when it is first used, so a second post with it goes to the row the first one made. The demo leaves it out: it needs a table of its own, and the row can be deleted | A token in the base, for a case the demo does not need |
| Rounding half up, `rounded()` in the formatters | What a person and Excel's `ROUND` expect, in one place for the screen and the export. Python's default, half even, would make a screen and a sheet disagree | Half even |
| Tabs on a detail page are links, not ARIA tabs | Each tab gets an address, which is how this base keeps state, and it works without JavaScript and with the back button. ARIA's pattern promises that arrow keys switch panels that are already there, which links are not | Real ARIA tabs, which fit panels all present on the page, and stay for those in `app.js` |
| Work orders fall unevenly on equipment, and carry eight titles | One order for each fifth machine under two titles made every history the same line. The frozen hash of the rows moved with it | Keeping the rows as they were |
| Chart.js loaded by our script, only where a chart is | 210 KB on every page is a cost for pages with no chart, and a macro that needs nothing in the page's head is one less thing to forget. It keeps its integrity. It also draws a figure that htmx brings | A script in the layout, on every page; a block each page must fill |
| Numbers reach a chart as text | No Decimal becomes a float on the server, and the only rounding is the browser drawing a line | A float for each value |
| A chart's table in a closed `details` | Always in the page, for a screen reader and without JavaScript, and it keeps a dashboard tidy | A table open under each chart: a dashboard twice as long |
| Polar area left out of the gallery, and supported | The owner asked for what looks good and adds something. It repeats a pie, its area exaggerates differences, and its scale sits on its slices | A poor example shown because it exists |
| Status colours for states, and four colours for series | A colour that says *stopped* cannot also mean *series three*. A pie with more than four parts borrows them, because the theme has no others | Generating hues, which would invent colours |
| Grouping and editing with a table and a form, not a grid | ARIA's grid asks for its own keyboard model, for cell focus and for row counts when rows are not in the page, and most grids deliver part of it. A native table and a dialog need none of that, and work without JavaScript. The price is one row at a time | Inline editing in cells; Tabulator, as above |
| A dialog for editing, not a form in the row | A row is too narrow for a form on a phone, a dialog keeps the keyboard, and a failed save stays where the person is | An inline form with htmx, which works too and would suit one short field |
| Equipment by its code, faults in the searchable select | Without JavaScript a searchable select is a plain select, which must hold every option, and 50,000 are megabytes in a page. A text box with a checked code works the same with and without JavaScript. A list of twenty faults is what a searchable select is for | A combobox that asks the server: more behaviour, and no fallback that still lets a person choose |
| After a save, the whole list comes back | A changed state or date can move the row to another group, or out of the filter. Replacing one row would leave it in the wrong place | Replacing the row alone |
| A version column, and a conflict that keeps what was typed | Two people on one row lost work in silence. SQLAlchemy's `version_id_col` puts the check in the `UPDATE`, which is the only place a save between a read and a write can be caught. The message lists what is saved now, so a person decides without another screen, and a second Save replaces it knowingly. A late save that matches the row is no conflict: a double click should not frighten anyone | The last save wins, as milestone 2 did. Comparing a timestamp: two saves can share one. Locking a row while a person edits: a lock left by a closed tab needs a timeout, and blocks everyone until then. Merging field by field: a business rule, not a base's to guess |
| An identifier has no thousands separator | It is a name, not a quantity: *4059* is how a person repeats it | Formatting every number alike |
| The demo's today is a fixed day | Overdue, charts and summaries must agree with each other and stay the same on any day, and a test must be able to read them. With the real date, every open order would be overdue a year from now | `date.today()`, which makes figures drift and tests depend on when they run |
| A chart chooses through the links of its table | The table is already there for a screen reader, so its links are the keyboard's way in, and a click on the picture follows the same link: htmx, the address and the focus are the table's, and `charts.js` adds a dozen lines. To filter in place, the list's own form goes with the chart's one value, so a chart drawn once never sends a filter that the list has since changed | Making the canvas focusable with its own keys, which no screen reader would know; links that carry the whole state of the list when the page was drawn, which go stale as soon as a person changes another filter |
| A board drawn on the server, a form on each card, and SortableJS to drag | The form is what a keyboard, a screen reader and a page without JavaScript already know, and dragging only fills it in, so there is one way to move a card and the server decides. SortableJS is MIT, about 15 KB compressed, drags by pointer and by touch, moves cards through the CSSOM and ran with no policy violation; it loads only where a board is | Dragula and Draggable: compared on the same board, with no gain for a heavier file. Native drag and drop: no touch. A board drawn in the browser: a second way to write screens |
| Ranks with gaps, numbered again when one runs out | Moving a card writes one row, and its version moves alone. Renumbering a column is rare, and goes through the table so that nobody else's form becomes a conflict | Decimal ranks, which run out of digits too; numbering the whole column on every move |
| A Gantt chart drawn on the server as SVG, beside its table | Every library compared broke the policy or the keyboard: none ran cleanly under it. The table already holds the rows, the dates and the actions for a keyboard and a screen reader, so the picture only shows when, with no behaviour of its own: about two hundred lines of Python and a macro, with colours from the theme | A Gantt library in the browser: none passed under this policy. A picture with its own controls, which would repeat the table's |
| The Gantt's picture is the one inline SVG, by name | Icons and illustrations stay files, so nothing in them can run. A chart of data drawn here from rows must follow the theme, which an image cannot, and it holds no text a person wrote but labels the macro escapes. The exception is one macro in one file, and a test checks what it draws as an image is checked | Serving it as an image from its own address: a second request with the same filters, and colours that cannot follow the theme |
| FullCalendar 7 for calendars, with the base's words, colours and checks | It was tried first, against every condition: no policy violation, no failure of the scan in light and dark, our own Spanish and Catalan, the theme's colours, month, week and agenda with the address, the application's time zone after a drag, a form for the keyboard and htmx. All held, with configuration, our locale object and its own variables, and no file of it changed. MIT, about 920 KB in five files, the library unminified as published; loaded only where a calendar is | A calendar drawn on the server, kept as the way back had a condition failed; Event Calendar: 42 failures of the scan for list roles, and dark contrast; FullCalendar 6, which needs named time zones from another library; its own locale files, wrong in Spanish |
| Chart.js for charts | Compared on the same data under this Content Security Policy, in light, dark and at phone width. 210 KB, MIT, no policy violation, and its own tooltip fits both themes. A canvas says nothing to a screen reader, so the summary and the data table are always there | ECharts: 1.1 MB, its default tooltip breaks under the policy and needs `richText`, and it has no Catalan. SVG drawn on the server: no JavaScript, but no interaction, and each chart to maintain here |
| Lucide's whole icon set in the repository, as a folder pinned by one hash | A person or an assistant can use any icon without a download or a decision, and the search works offline. Lucide is ISC, has no brand logos by policy, and its icons share one grid and stroke. 1,891 icons, 0.9 MB in 1,892 files, about 420 KB packed in git.
