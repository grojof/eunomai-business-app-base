# Specification

`business-app-base` is a working application that demonstrates its own components. An organization clones it once and
adds its brand; each new application is then a clone of that copy, with the demo deleted.

Success means three things, each testable:

| Goal | Test |
|---|---|
| Adapting it to an organization is cheap | Changing only `app/brand/` and the settings gives that organization's look |
| A new application starts clean | With `app/demo/` deleted, every tool check and the tests still pass |
| The components hold the [standards](standards.md) | Only components marked *Not recommended* may fail the [gallery](#gallery)'s scan |

## Structure

```text
app/
  core/      identity, roles, settings, languages, formatters, errors, health
  ui/        components: catalog.py, Jinja macros, the stylesheet's source, app.js, vendored htmx
  brand/     theme.css, logo.svg
  demo/      screens, their fixed values, translations
locales/     the translations of core and ui
tests/
tools/       stylesheet, component pages, translations, CLDR data, copied files, dependency update, demo removal
docs/
  components/  one page per component, generated, and catalog.json
```

Planned, and not there today:

| Folder | Contents | Arrives in |
|---|---|---|
| `app/core/` | The database connection | Milestone 2 |
| `app/demo/` | Models and generated sample data | Milestone 2 |
| `migrations/` | Alembic | Milestone 2 |
| `deploy/` | Example service files and the [registration](#registration) file | Milestone 5 |
| `app/brand/` | Fonts | Milestone 6 |

## Stack

These two tables are the approved list: a dependency in neither needs a [decision](decisions.md) first. Exact versions
live in `uv.lock` and `vendor.json`, not in this page.

In use today:

| Piece | Choice |
|---|---|
| Server | Python 3.12+, FastAPI, Pydantic v2 with pydantic-settings, Uvicorn; uv with `uv.lock` |
| Pages | Jinja2 with escaping always on, htmx 2.0 |
| Styles | Tailwind CSS 4 with daisyUI 5, generated by Tailwind's standalone executable. Recommended, not required: applications call macros, so an organization can replace this layer in `app/ui/` |
| Languages | gettext catalogues through Babel and Jinja2's i18n extension |
| Support | python-multipart for posted forms; tzdata, because Windows has no time zone database |
| Development | pytest, httpx2, Playwright for Python, axe-core, Ruff, mypy |

Approved, not added yet:

| Piece | Choice | Arrives in |
|---|---|---|
| Data | PostgreSQL, SQLAlchemy 2, Alembic, psycopg 3 | Milestone 2 |
| Reading another system's SQL Server | pyodbc with Microsoft's ODBC Driver 18 and a read-only user | Milestone 2, optional |
| Tables | Made on the server; Tabulator only where grouping or editing needs it ([open](decisions.md#open-questions)) | Milestone 2 |
| Charts | Apache ECharts ([open](decisions.md#open-questions)) | Milestone 2 |
| Excel | XlsxWriter, on the server | Milestone 2 |
| Page behaviour | Alpine.js in its CSP build | Milestone 3 |

No Node, no npm and no file loaded from another server. The stylesheet is generated by one executable, checked against
its hash on every run, and the generated `app.css` is committed, so servers need nothing but the application. Inside an
assistant's sandbox, this was confirmed only as far as the executable downloading, matching its hash and starting, on
one account: a full stylesheet has not been generated there.

`vendor.json` lists every third-party file that is not a Python package, with its version and hash. All are copied
into the repository except Tailwind's executable. The one pages load, htmx, is served with Subresource Integrity.

## Dependencies

A daily workflow keeps dependencies current, and every clone inherits it. It updates to the newest version the rules
allow, runs the tests and proposes one pull request, which a person merges. While a problem remains, an issue stays
open. *Reported* below means exactly that: the problem goes to the issue, the version stays and the update goes on.

| Rule | Python packages, `uv.lock` | Copied files, `vendor.json` |
|---|---|---|
| Known vulnerability | Moves to the newest version without one; if none exists, or the limits refuse it, Reported | A vulnerable version is never chosen; if nothing else qualifies, Reported |
| Pre-release | Reported if locked | Never chosen |
| Yanked | Reported if locked | Not checked: npm has no such state |
| Deprecated | Not checked: PyPI has no such state | Never chosen; Reported if it is the current version and nothing newer qualifies |
| Released less than two weeks ago | Waits, unless it fixes a vulnerability in the locked version | Waits, unless it fixes a vulnerability in the current version and every settled newer version has one too |
| No release in three years | Reported, unless listed in `EXCEPTIONS` in `tools/update_dependencies.py` | Not checked |
| No `https` address in its published metadata | Reported, unless listed in `EXCEPTIONS` in `tools/update_dependencies.py` | Not checked |
| New major version | Never automatic for a direct dependency: `pyproject.toml` sets its upper limit, except for tzdata, whose versions are dates. A package only others need moves as far as they allow | Never automatic: it takes a decision, as htmx 4 does |
| Older version | Not checked | Never: a file stays where it is rather than go back |

If a new daisyUI file breaks `docs/components/`, such as a new or removed component or a changed format, daisyUI stays
at its version, an issue says why, and everything else goes ahead. Any failed update opens the issue too. The job that
runs upgraded code can only read; a separate job, which runs no project code, opens the pull request, and accepts only
the files the update produces.

Each copied file is pinned, and the same version with different bytes is refused:

| File | Pinned by |
|---|---|
| A package from npm | The integrity the registry publishes |
| Tailwind's executables | The release's `sha256sums.txt` |
| daisyUI's `.mjs` files | A hash recorded on first download: daisyUI publishes no checksum for them |
| daisyUI's `llms.txt` | A hash of what [the rebuild](#documentation-for-assistants) gives |

A new version of any of these files is accepted on the two-week rule. Its checksum proves it is what was published, not
that it is good, and the `.mjs` files do not have even that.

## Identity

The application has no login of its own. A trusted reverse proxy authenticates the person and passes who they are in
headers; the header names and the mapping from groups to roles are settings. Those headers are believed only from the
addresses in `APP_TRUSTED_PROXIES`, by default this computer. Uvicorn listens on `127.0.0.1` by default and must run
with `--no-proxy-headers`: otherwise it replaces the proxy's address with the one in `X-Forwarded-For`, and everyone
gets 401. A repeated identity header means no identity.

A visitor without identity gets the 401 page, with no navigation, version or user menu. The public paths are exactly
`/health` and `/static/`. For local work, a fake identity is available and refuses to start outside development.

## Layouts

An application chooses its arrangement in its settings. The demo's *Layouts* page shows each one live.

| Setting | Options | Typical use |
|---|---|---|
| `APP_LAYOUT_NAVIGATION` | `side`, `compact` (icons only), `top`, `hidden` (opened from a button) | Side for management applications; top for a few sections |
| `APP_LAYOUT_STICKY_HEADER` | `true`, `false` | Fixed for long tables |
| `APP_LAYOUT_WIDTH` | `full`, `centered` | Full for tables; centred for forms |
| `APP_LAYOUT_DENSITY` | `normal`, `compact` | Compact for data-heavy screens |

On a phone the navigation is always a panel opened from a button.

## Components

A component is one Jinja macro or one piece of the shell, using only the brand's colours. Screens call macros, not
daisyUI classes, so the look can change in one place. Each macro appears in the demo's *Component catalogue*, and has
tests. The macros today are `icon`, `page_heading`, `message`, `button`, `card`, `stat` and `empty_state`.

| Group | Components | Since |
|---|---|---|
| Structure | Page layout, header, navigation, skip link, page heading, user menu (identity, language, theme, version), button, card, icon | Milestone 1 |
| Data | Indicator tile | Milestone 1 |
| Feedback | Message banner, announcement region, empty state | Milestone 1 |
| Pages | No identity (401), no permission, not found, server error | Milestone 1 |
| Structure | Breadcrumbs | Milestone 2 |
| Data | Server table (paging, sorting, filtering, state in the URL, row actions), rich table, filter bar, pagination, description list, tabs, status label, chart with its data table | Milestone 2 |
| Output | Excel export, print style | Milestone 2 |
| Forms | Text, text area, select, checkbox, radio, date, number and decimal, searchable select, file upload, error summary, field error, form actions | Milestone 3 |
| Feedback | Confirmation dialog | Milestone 3 |
| Feedback | Loading state, progress of a long task | Milestone 4 |
| Pages | Service unavailable | Milestone 4 |

A component is left out until a real need appears for it. The base stays small enough to read.

## Gallery

The gallery shows every free daisyUI component, live and in the current theme, so a person can see what is available and
ask for it by name.

| Status | Meaning |
|---|---|
| Approved | A macro, tests and a review. This is what applications should use. Today: `alert`, `button` and `card` |
| Available | Passes the automatic scan. Usable with care |
| Decorative | Not meant for management applications |
| Not recommended | Fails a standard; its note states why |

`app/ui/catalog.py` is the one list. It survives deleting the demo, and it feeds the gallery, the documentation and
`catalog.json`.

The checks prove that an *Available* component passes the automatic scan. They cannot prove the opposite: *Decorative*
and most of *Not recommended* are a person's judgement, such as text that moves on its own, and *Approved* needs the review
its name says.

For most components the gallery shows every colour, style and size daisyUI offers. Those lists are not written by hand: `tools/components.py` takes them from the official file into `app/demo/variants.json`, so a new variant appears by itself. *Not recommended* components have a better option in this base, and their note names it.

A component in the gallery is available to use, not yet used: real screens use only `alert`, `button`, `card`, `dropdown`, `menu`, `navbar` and `stat` until milestones 2 to 4 bring the rest.

## Documentation for assistants

An assistant should load only what it needs. `tools/components.py` cuts daisyUI's official `llms.txt`, about 20,000
tokens, into one page per component of about 375 tokens on average, counting 4 characters per token, each with OKF-style
frontmatter. Nothing is interpreted: the file is cut at its headings, and a test fails if a page drifts from it.

| File | Read |
|---|---|
| `docs/components/README.md` | First: what exists, with its status and use |
| `docs/components/rules.md` | Once: how classes and colours are used |
| `docs/components/<name>.md` | Only for the components in use |
| `docs/components/catalog.json` | The same list, for programs |

daisyui.com serves only the latest `llms.txt`, so `tools/vendor.py` rebuilds it from the files at the version's git tag,
the way the site builds it. For the pinned version, the result is identical to the site's file. If the site's build file
changes, the hash in `vendor.json` refuses the rebuild until a person has compared the two.

The generator stops rather than guesses, in each of these cases:

| Case | Why it needs a person |
|---|---|
| A component in the official file but not in `app/ui/catalog.py` | Its status is a decision |
| A generated page whose component left the official file | It is stale |
| A hand-written page on an official name | Generating would overwrite it |
| A catalogue entry with no official section and no page of its own | There is nothing to read |
| A page with no description, or an official section with no description or documentation link | The index would be empty, or the format changed. A description may be plain or quoted YAML |

Where daisyUI's text disagrees with this repository, such as its advice to use a CDN or `npm`, this repository wins, and
each page says so.

## Adapting it

| To do this | Change |
|---|---|
| Your colours, radius and logos | The base uses daisyUI's `light` and `dark` themes as they come. To change them, paste what [daisyUI's theme generator](https://daisyui.com/theme-generator/) gives you into `app/brand/theme.css`, in hex or oklch, and run `tools/css.py`. Contrast of your theme's text colours is then computed |
| Another CSS library | `app/ui/`: the macros and the stylesheet's source; screens do not change |
| Your languages | Each folder under `locales/` is a required language: add yours, run `tools/translations.py update` and translate it. Change `APP_LANGUAGES` too |
| Your time zone | `APP_TIME_ZONE`; the default is UTC |
| Your identity proxy | Settings: `APP_TRUSTED_PROXIES`, `APP_HEADER_*`, `APP_GROUPS_SEPARATOR`, `APP_ROLE_GROUPS` |
| Start an application | Clone your copy and run `tools/remove_demo.py`, then `tools/css.py`. It deletes the demo with its tests and icons, renames `demo-admins` in `.env.example`, and turns the rules only the demo proved to *By hand* |
| Add your own component | A macro in `app/ui/`, its line in `app/ui/catalog.py`, and a page in `docs/components/`. Only `description` is required in the page's frontmatter; do not put the `Generated by tools/components.py` marker in it. `tools/components.py` keeps your page and adds it to the index. An approved component needs `macro=` in its line. In your organization's base, add its specimen to the gallery; applications have no gallery |

An application that needs something different changes it: the code belongs to whoever cloned it. There is no update
mechanism. When the base improves, an application compares versions and takes what it wants.

`AGENTS.md`, the documentation and the checks travel with every clone. Any of them can be removed and the application
still runs.

## Checks

| Check | What it proves |
|---|---|
| Unit and integration tests | Behaviour, including permissions per role |
| Tests with `app/demo/` deleted | In a copy without the demo, the stylesheet builds, every tool check passes and the tests pass, browser tests included |
| Accessibility scan, in both themes | No automatically detectable failure on the start, error, catalogue, layouts, administration and gallery pages, or in any layout. Components marked *Not recommended* are left out |
| Brand contrast | Each text colour of a theme added to `theme.css` against its background |
| Keyboard tests | Every control of the start page is reached with visible focus; focus stops clear of the sticky header; Escape closes the user menu, the phone menu and a dialog, and returns focus |
| Tab order | The Tab key visits the visible controls in the order of the page, on the start page and on a page full of controls |
| Language checks | See [Standards](standards.md#how-language-is-checked) |
| Rule tracing | Every rule has a source and a check. Tests are read from pytest's collection, so a comment or a string cannot pass as one, and no *Automatic* rule lacks its test |
| Invented values | No invented colours or sizes in templates, including `[color:#ff0000]`, and Tailwind's palette removed |
| Invented classes | Every class in use generates CSS, as [COMP-04](standards.md#components) says |
| Generated stylesheet | `tools/css.py check`: `app.css` matches the templates |
| Component pages | `tools/components.py check`: `docs/components/` matches the official file and the catalogue |
| Copied files | `tools/vendor.py check`: each file matches its recorded hash |
| Linter, type checker, lock file, [dependency rules](#dependencies) | The code and its dependencies |

Browser tests use Playwright for Python and a vendored axe-core. Both are development tools: no server needs them.

## Registration

Planned for milestone 5. `deploy/registration.toml` will describe the application to the platform that hosts it:
identifier, name, group, icon, port, limits, public paths, and each role with the directory group that grants it. A
hosting platform can generate its web server and access configuration from this file. Its fields are fixed against a
real platform.
