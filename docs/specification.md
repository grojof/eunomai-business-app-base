# Specification

`business-app-base` is a working application that demonstrates its own components. An organization clones it once and
adds its brand; each new application is then a clone of that copy, with the demo deleted.

Success means three things, each testable:

| Goal | Test |
|---|---|
| Adapting it to an organization is cheap | Changing only `app/brand/` and the settings gives that organization's look |
| A new application starts clean | With `app/demo/` deleted, every tool check and the tests still pass |
| The components hold the [standards](standards.md) | Real screens pass the scan in both themes, and approved components have tests and a review. Official examples in the [gallery](#gallery) are reference material: no gate |

## Structure

```text
app/
  core/      identity, roles, settings, database, exact column types, server lists, reading forms, languages, formatters, errors, health
  ui/        components: catalog.py, Jinja macros, settings, palette, the stylesheet's source, app.js, charts.js, vendored htmx and Chart.js
  brand/     theme.css, logo.svg
  demo/      screens, their fixed values, models and generated data, the gallery with its generated examples/, translations
locales/     the translations of core and ui
migrations/  Alembic: how it reaches the database, the template of a migration, and versions/
tests/
tools/       stylesheet, component pages, gallery data, translations, CLDR data, copied files, dependency update, demo removal
docs/
  components/  one page per component, generated, and catalog.json
```

Planned, and not there today:

| Folder | Contents | Arrives in |
|---|---|---|
| `deploy/` | Example service files and the [registration](#registration) file | Milestone 5 |
| `app/brand/` | Fonts | Milestone 6 |

## Stack

These two tables are the approved list: a dependency in neither needs a [decision](decisions.md) first. Exact versions
live in `uv.lock` and `vendor.json`, not in this page.

In use today:

| Piece | Choice |
|---|---|
| Server | Python 3.12+, FastAPI, Pydantic v2 with pydantic-settings, Uvicorn; uv with `uv.lock` |
| Pages | Jinja2 with escaping always on, htmx 2.0, and plain JavaScript in `app/ui/static/app.js` for the little that is left |
| Data | PostgreSQL in production, SQLite for the demo and previews; SQLAlchemy 2, Alembic, psycopg 3 with its binary package |
| Styles | Tailwind CSS 4 with daisyUI 5, generated by Tailwind's standalone executable. Recommended, not required: applications call macros, so an organization can replace this layer in `app/ui/` |
| Languages | gettext catalogues through Babel and Jinja2's i18n extension |
| Tables | A native HTML table with daisyUI's classes; paging, sorting, filtering and grouping on the server |
| Excel | XlsxWriter, on the server |
| Charts | Chart.js, with a text summary and the data as a table |
| Support | python-multipart for posted forms and uploads; tzdata, because Windows has no time zone database |
| Development | pytest, httpx2, Playwright for Python, axe-core, Ruff, mypy |

Approved, not added yet:

| Piece | Choice | Arrives in |
|---|---|---|
| Reading another system's SQL Server | pyodbc with Microsoft's ODBC Driver 18 and a read-only user | Milestone 2, optional |

No Node, no npm and no file loaded from another server. The stylesheet is generated by one executable, checked against
its hash on every run, and the generated `app.css` is committed, so servers need nothing but the application. Inside an
assistant's sandbox, this was confirmed only as far as the executable downloading, matching its hash and starting, on
one account: a full stylesheet has not been generated there.

`vendor.json` lists every third-party file that is not a Python package, with its version and hash. All are copied
into the repository except Tailwind's executable. The ones pages load are served with Subresource Integrity: htmx on
every page, and Chart.js, marked `on_demand`, only where a chart is.

## Dependencies

A daily workflow keeps dependencies current, and every clone inherits it. It updates to the newest version the rules
allow, runs the tests and proposes one pull request, which a person merges. While a problem remains, an issue stays
open. *Reported* below means exactly that: the problem goes to the issue, the version stays and the update goes on.

| Rule | Python packages, `uv.lock` | Copied files, `vendor.json` |
|---|---|---|
| Known vulnerability | Moves to the newest version without one; if none exists, or the limits refuse it, Reported | A vulnerable version is never chosen; if nothing else qualifies, Reported |
| Pre-release | Reported if locked | Never chosen |
| Yanked | Reported if locked | Not checked: npm has no such state |
| Deprecated | Not checked: PyPI has no such state | Never chosen; Reported if it is the current version and nothing newer qualifies |
| Released less than two weeks ago | Waits, unless it fixes a vulnerability in the locked version | Waits, unless it fixes a vulnerability in the current version and every settled newer version has one too |
| No release in three years | Reported, unless listed in `EXCEPTIONS` in `tools/update_dependencies.py` | Not checked |
| No `https` address in its published metadata | Reported, unless listed in `EXCEPTIONS` in `tools/update_dependencies.py` | Not checked |
| New major version | Never automatic for a direct dependency: `pyproject.toml` sets its upper limit, except for tzdata, whose versions are dates. A package only others need moves as far as they allow | Never automatic: it takes a decision, as htmx 4 does |
| Older version | Not checked | Never: a file stays where it is rather than go back |

If a new daisyUI file breaks `docs/components/` or the [gallery](#gallery), such as a new or removed component or a
changed format, every daisyUI file stays at its version, an issue says why, and everything else goes ahead. They move
together or not at all. Any failed update opens the issue too. The job that
runs upgraded code can only read; a separate job, which runs no project code, opens the pull request, and accepts only
the files the update produces.

Each copied file is pinned, and the same version with different bytes is refused:

| File | Pinned by |
|---|---|
| A package from npm | The integrity the registry publishes |
| Tailwind's executables | The release's `sha256sums.txt` |
| daisyUI's `.mjs` files | A hash recorded on first download: daisyUI publishes no checksum for them |
| daisyUI's `llms.txt` | A hash of what [the rebuild](#documentation-for-assistants) gives |
| daisyUI's documentation source | A hash of the file collected from the version's tag, for the [gallery](#gallery) |

A new version of any of these files is accepted on the two-week rule. Its checksum proves it is what was published, not
that it is good, and the `.mjs` files do not have even that.

The PostgreSQL image the tests run on is pinned by digest in `tests.yml`, at the newest one past the two weeks. No
workflow moves it: a person does.

## Data

PostgreSQL is the real database. SQLite is the default for the demo and for previews, so a clone runs with nothing
installed. It never runs in production.

| Setting | Effect |
|---|---|
| `APP_DATABASE_URL` | Where the data is. By default `sqlite:///.data/app.db`, a file git ignores, made by the first connection |
| `APP_ENVIRONMENT` | `production` by default, and production refuses anything but PostgreSQL. `.env.example` sets `development` |

So a server with neither setting stops as it starts, and says what to set.

```bash
uv run --frozen alembic upgrade head               # applies the migrations
uv run --frozen python -m app.demo.generate        # applies them too, then fills the demo's tables, in seconds
uv run --frozen alembic revision --autogenerate -m "What changed"   # after changing a model; read what it wrote
```

A route asks for a session and declares itself with `def`, so a query runs in a worker thread instead of stopping the
server. Nothing is saved unless the route commits, so a failed commit can still reach the person:

```python
def close_order(order_id: int, session: DatabaseSession) -> Response:
    session.get(WorkOrder, order_id).closed_at = datetime.now(UTC)
    session.commit()
```

### Column types

Models inherit from `Base`, in `app/core/database.py`. Annotations choose the type, so the exact one needs no asking.

| In a model | PostgreSQL | SQLite | In Python |
|---|---|---|---|
| `Mapped[Decimal]`: money and quantities, 18 digits and 20 decimals | `numeric(38, 20)` | Text in one form: `1.50` is `1.5`, with the collation `exact_decimal` | `Decimal`, without trailing zeros on both |
| `Mapped[datetime]`: a moment | `timestamptz` | Text of a fixed width, in UTC | An aware `datetime`, in UTC |
| `Mapped[date]`: a day in the calendar | `date` | Text, `2027-03-15` | `date` |

A float is refused on writing and in a query, and so is a `datetime` without its time zone. So is a value the column
cannot hold whole: PostgreSQL alone would round extra decimals without a word, so both databases refuse them here.

### Decimals on SQLite

SQLite has no exact number. Stored as text, an exact column would order as letters, 100 before 9, and `SUM` would turn it
into a float. Neither is allowed to happen in silence:

| Over an exact column | On SQLite | What to use |
|---|---|---|
| `ORDER BY`, `<`, `>`, `BETWEEN`, `=`, `min`, `max`, `count` | Numeric: the collation compares each pair as `Decimal`, in Python | The same query as on PostgreSQL |
| `sum`, `avg` or any other function, arithmetic, `CAST`, `CASE` | `InexactQuery`, before the statement runs | `total()`, which sums in SQL on PostgreSQL and in Python on SQLite, or `exact_sum()` on values already read |

`exact_sum()` exists because Python's own `sum` rounds to 28 digits without an error.

`InexactQuery` reads statements built with SQLAlchemy. **SQL written by hand with `text()` is not read**: its `ORDER BY`
is still numeric, because the collation belongs to the column, but its `SUM(cost)` gives a float. Such a query over an
exact column is for a person to catch in review.

### Where the two databases differ

| What | PostgreSQL | SQLite |
|---|---|---|
| Ordering an exact column | Native, and can use an index | A Python call per comparison. With an index on the column a page of 50,000 rows takes under a millisecond, because the comparisons were paid when the index was written. Without one, about 0.65 seconds |
| Reading the file with another tool | Not applicable | Ordering an exact column stops with `no such collation sequence`, and foreign keys may be off |
| Sums and arithmetic in SQL | Exact | Refused, as above |
| `String(40)` | Enforced | Not enforced: longer text is stored |
| `LIKE` | Tells capitals apart | Does not, for ASCII |
| Ordering text | By the database's collation | By bytes |
| Writers at once | Many | One |
| A migration that fails | Undone whole | May stay half applied: delete `.data/` and generate again |
| Changing a table | `ALTER TABLE` | Batch mode: copies the table, drops the old one, renames the copy. Foreign keys are off for that, and checked after it. SQLite reports no collation when a table is read, so `app/core/database.py` listens to every reflected table and puts it back. `alembic check` cannot see a lost one: a test walks each migration down one and up one and compares what the file really holds |
| Foreign keys | Always on | On per connection, by `create_database_engine` |

The tests of the database layer run on both, so a difference that breaks them shows. Those that stay are the table above:
a query that depends on one passes on one database and not the other.

### Lists on the server

`app/core/tables.py` is what a long list needs, and it stays when the demo goes. A route describes its columns and filters
in a `ListView`, which reads the address, and the macros `filter_bar`, `list_summary`, `server_table` and `pagination`
draw it:

```python
view = ListView.read("orders", "/orders", request.query_params, columns, Order.id, "opened", filters, searched, label)
view.load(session, select(Order))
return render_list(request, view, "orders/list.html", "orders/results.html")
```

| What | How |
|---|---|
| State | In the address: `q`, each filter, `sort`, `dir`, `size`, `page`. Defaults are left out, so one state has one address, and it can be bookmarked, reloaded and shared |
| Input | Each value is checked against its list in `ListView.read`, and `list_query` reads the address a person came from, keeping blank values, which mean something, and ignoring what it cannot read. A value outside its list is ignored, so an old bookmark still opens. A sort name selects a `Column` by key, so nothing from the address reaches SQL as text, and the search term is a bound parameter with `%` and `_` escaped |
| Order | A tiebreak on the primary key keeps rows from moving between pages. A column marked `nullable` puts empty values last on both databases, which by themselves disagree |
| A label sorts as read | The database cannot sort what it does not hold. `case` gives each stored value its position, as the demo's locations do in the person's language and its states by what needs attention first. Such a column uses no index: about 10 milliseconds at 50,000 rows |
| Without JavaScript | Headers and pages are links, and filters are a GET form with an Apply button |
| With htmx | The same address answers with its results alone, and `whole_page` sends a person to a whole page when there are no results to give, because htmx would put a redirected page inside the fragment. `Vary: HX-Request` keeps the two apart, and `HX-Push-Url` gives the address its one form. History is not kept in the browser: going back reloads the address, so a form can never show an older state than the table, and no row is left in `localStorage` |
| Focus | htmx puts it back on an element that kept its id, as a sort header does. If none did, as the Next link on the last page, `data-focus-fallback` takes it |
| A request that fails | `app.js` shows a message for every htmx failure, on any screen, inside an open dialog if there is one, with `role="alert"`. A 404 says the thing is no longer there, and a row removed while it was being saved gets that same 404 |
| Announcement | `data-announce` on the summary goes to the announcement region after each change: rows, order and direction |

Measured on one laptop, on SQLite with 50,000 rows and the demo's indexes: the first page takes 0.6 milliseconds whether
it sorts by code or by cost, the last page 4, a search 27. A whole request, with its page drawn, takes 10 to 30.

### Charts

`app/core/charts.py` makes what a figure shows, and the macro `chart` draws it: a `<figure>` with its title and summary, a
canvas, and always the same numbers as a table. A route works out the numbers and passes them as `Decimal`. They travel
to the browser as text, as JSON in a `<script type="application/json">`, which nothing runs, so no float appears on the
server. `app/ui/static/charts.js` reads that JSON and loads Chart.js, once, with its integrity, when a page has a chart.

```python
data = chart_data(months, [Series(_("Planned"), planned), Series(_("Worked"), worked)], _("Month"), unit=_("h"))
```

```jinja
{{ chart(_("Hours planned and worked"), _("Hours worked stayed within 6 % of the plan."), data, "bar", "chart-hours") }}
```

| What | How |
|---|---|
| Types | `bar`, `stacked`, `line`, `area`, `pie`, `doughnut`, `radar`, `scatter`, `bubble`, `mixed` and `polar`. Scatter and bubble use `point_data`. Polar area is drawn and tested, and left out of the gallery: it says what a pie or a bar says, less well, because area grows with the square of the value |
| One axis | A mixed chart has one scale. Two measures of different size are two charts |
| Colours | Read from the theme's CSS variables, and turned to rgb by painting one pixel, because the themes use oklch and Chart.js cannot mix that. Series take `primary`, `accent`, `secondary`, `info`, in that order. A fifth series is refused: it should be another chart. `success`, `warning` and `error` are for states. `neutral` is left out: on the dark theme it cannot be told from the page |
| A change of theme | Colours follow with no reload, whether the system changes, `data-theme` does or a theme control does. A series hidden in the legend stays hidden |
| Hover | On bars and lines, the `index` interaction and a thin guide line on the month, from a small plugin of ours. On pie and doughnut the slice grows, with `hoverOffset` |
| Language | Numbers in tooltips and axes use the page's locale through `Intl`, and large axes use its compact form. Chart.js has no text of its own on these charts: every word comes from the server, translated |
| Motion | None if a person asks for `prefers-reduced-motion` |
| Without the picture | Without JavaScript the canvas is hidden and the summary and table remain. If Chart.js fails to load, or one chart fails to draw, its table opens by itself, and no other chart stops |
| What is refused | A colour outside the list and a negative value in a pie, a doughnut or a polar area are errors on the server, while the code is written. Chart.js would draw the negative as positive |
| On a phone | Every label that fits stays. When they do not all fit they spread evenly and the first and the last always stay, which Chart.js's own thinning does not promise: it left out October. A chart keeps its height |

daisyUI's colours pass the checks for colour blindness (neighbouring series stay apart) and normal vision, on both
themes. `accent` and `warning` are light, at 1.9:1 against white, under the 3:1 of A11Y-14. The base keeps the themes as
they come, so the legend, the summary and the table carry what those marks cannot. An organization can solve it in its
theme.

### Groups and editing a row

The planning screen is what a spreadsheet-like grid would be asked for, without one. People who need to change one work
order among thousands get a native table and a native form, which a screen reader and a keyboard already know, with
nothing to learn in between.

| What | How |
|---|---|
| Groups | `grouped_table` writes one `<tbody>` per group, with a header row and `scope="rowgroup"`. The group goes first in `ORDER BY`, so paging and sorting work inside it. Grouping is a filter with no condition: it lives in the address like the rest |
| Totals | The whole group's, not the page's. `totals_by` groups in SQL on PostgreSQL. SQLite cannot add exact columns, so it adds in Python, with the same answer. A group cut by a page says *continued* |
| Editing | One row at a time, in a native `<dialog>` that htmx fills. The browser keeps the keyboard inside, and Escape closes it. Without JavaScript the same address is a page of its own |
| Saving | A POST, checked by `_context` as [SEC-07](standards.md#security) says: a request from another site is refused before it reaches the route. Editing needs the `admin` role, on the server, and without it the Edit action is not offered |
| Errors | Listed at the top of the form, each a link to its field, with focus on the list. What was typed stays. [Forms](#forms) grow from this |
| After a save | The list comes back in the order and on the page it was, because the row may now belong to another group, or to none. Focus returns to the row's Edit link, or to the table if the row left the list. A message says what was saved, on screen and to a screen reader, and without JavaScript too: the address carries `saved` for that one page |

### Two people on one row

A row that people edit has a version. The form carries the version it was read at, and a save compares it. Both the
planning editor and the work order form do this.

```python
class WorkOrder(Base):
    version: Mapped[int] = mapped_column(server_default="1")
    __mapper_args__ = {"version_id_col": version}
```

| What | How |
|---|---|
| Finding out | SQLAlchemy adds `AND version = ?` to each `UPDATE` and `DELETE`, and moves the number on. So a save that falls between another person's read and write changes no row, on either database, and `saved(session, change)`, from `app/core/database.py`, says so. A change of several steps goes in `change`, because loading anything flushes what came before it, and the check fires there. Comparing in Python alone could not catch that |
| Telling | The form comes back with what was typed and a [conflict notice](components/conflict-notice.md) that lists what is saved now, with focus on it. A 409 page without JavaScript, the same dialog or form with htmx. Saving again replaces their work, knowingly: the form now carries the newest version |
| Saying the same | A late save that matches the row is no conflict, so a double click or two people who agree meet no message |
| Wrong values first | A form with errors shows those, and keeps its old version, so the conflict comes on the next save |
| Deleting | A confirmation names what will go, each file by name, and carries what it named, so if the row or its files changed it asks again with what is there now |
| Files | Adding or removing a file changes no version: two people can each add one and neither loses anything. A file sent with a conflict, or for a row that has gone, is taken away again on every way out, and the form says to choose it again |
| A row removed meanwhile | The same 404 as ever. A failed `WHERE version` is read again to tell the two apart |
| Limits | Only saves through these forms are compared. A script that writes with `update()` moves no version unless it says so |

To give another table a version: the two lines above and a migration, then a hidden `version` in the form,
`read_version` and `saved` in the route, as `app/demo/planning.py` does.

### Forms

The work order form is the pattern of the planning editor, grown up: `/work-orders/new` and `/work-orders/<id>/edit`,
reached from Planning and from the equipment detail, and needing the `admin` role, as editing does.

| What | How |
|---|---|
| Fields | One macro per kind of field, all with a visible label, as the [gallery](#gallery) shows. A hint and an error reach the control through `aria-describedby`, and `aria-invalid` marks the error |
| Checking | `app/core/forms.py`, at the edge, as [SEC-03](standards.md#security) says. A reader takes text and gives the value to save, or raises `Refused` with what the person should read. `read_fields` runs them all, so every problem shows at once. The browser's `required` and `maxlength` help a person; forms are `novalidate`, and the server decides |
| Text | Trimmed, one form of line break, its length checked, and no control characters: PostgreSQL refuses a NUL, which would be an error page there and stored on SQLite |
| Numbers and dates | `read_decimal` and `read_whole` through `parse_decimal`, and `read_date` through `parse_date`, with limits, because a year typed as 0026 is a valid date and a mistake. Never a float. Generated costs have twenty decimals, so the cost field shows every one and a form nobody changed saves the same value |
| A failed save | The form comes back with what was typed, an error summary whose links land on the fields, and focus on it. A 422 page without JavaScript, the form alone in its place with htmx |
| A date typed halfway | A browser sends such a field as nothing, which would clear an optional date in silence, so `app.js` tells the server, and it asks for the date. The value cannot come back: the browser does not give it |
| A saved form | Back where the person came from, Planning or the equipment page, with their filters. The address says what happened, for that one page, as `saved` or `deleted`; a number that does not fit says nothing. `way_back` rebuilds the address from what it can read, so it never leaves those two screens |
| Deleting | With a [confirmation](components/confirmation-dialog.md) that names the row, in a dialog with htmx, and on a page of its own without JavaScript. The form that deletes is a plain POST in both |
| A form that is not one | A file sent for a text field or a part too long is a 400 page. FastAPI's own answer repeats what was sent |

The equipment is asked for by its code. A searchable select holds its options in the page, because without JavaScript it
is a plain select, and 50,000 of them is a page of megabytes. So the searchable select is the list of faults.

### Uploads

`app/core/uploads.py` answers [SEC-12](standards.md#security). What a file calls itself proves nothing, so a file passes
only if its name is safe and its first bytes say what its extension says.

| What | How |
|---|---|
| The list | PDF, PNG and JPEG, each with its signature, in `KINDS`. A kind needs a signature to join: plain text or CSV has none, and needs a reader of its own. The browser's `accept` helps a person choose and decides nothing |
| Refused | Too big, empty, a type off the list, a renamed extension, a real file under another kind's name, a path or a special character in the name, and a double extension. `report.v2.pdf` is refused with them: a rule with no exceptions is one that cannot be got round, and the message says what to do |
| Stored | Under a random name of ours, with no extension and only the application able to read it, in `APP_UPLOAD_FOLDER`. By default that is `.data/uploads`, which git ignores, and a folder inside `app/` stops the application from starting. The folder appears with the first file |
| Sent back | Reached only by the numbers of the order and the file, for the `admin` role, as an attachment, with `nosniff` and never cached. No path is built from anything a person sent: the stored name comes from the database and is checked again |
| Limits | `APP_UPLOAD_MAX_BYTES`, 10 MB, for a file, and `APP_REQUEST_MAX_BYTES`, 32 MB, for any request, on every route, because the framework reads a form to disk before any route runs. A declared length refuses a body early, and every body is counted as it arrives, whatever its headers say. A request with both `Content-Length` and `Transfer-Encoding` is a 400, unread. Between the two, a person gets an error on the field and keeps what was typed. Past the second, a 413: a message with htmx, with the form intact, and a page without JavaScript |
| A failed save | A browser cannot keep a chosen file when a form comes back, so the field says to choose it again. Nothing is stored until the whole form passes |
| Removing | With a confirmation that names it. Deleting an order names the files that go with it. A file leaves the disk after its row, so a failure leaves an untidy file, never a row without one, and the log says so. `app.demo.generate` empties the folder of stored files, because their rows have gone |

**What a clone must add for production.** This is a floor. Each of these depends on where the application lives, so none
is in the base:

| Add | Why |
|---|---|
| Virus scanning, with the file held back until it passes | A real PDF or JPEG can carry something harmful. Signatures say what a file is, not that it is good. Run a scanner such as ClamAV between the upload and the moment anyone can download it |
| A limit at the reverse proxy, below `APP_REQUEST_MAX_BYTES` | It stops a long body before Python sees it, and answers cleanly: an application that answers without reading the body can have its connection reset |
| Storage that fits the deployment | A local folder works on one server. Several servers need a shared volume or an object store, with `UploadStore` behind the same four calls, and a backup that moves together with the database |
| Quotas and a rate limit, per person | Without them one person can fill the disk, 10 MB at a time |
| Reading images again, where they are shown | Files here are only downloaded. An application that shows an image should decode it and write a new one, which drops what was hidden in it, and serve it from another origin |
| A record of who added, downloaded and removed what | The demo keeps a moment and no name. A real application needs its audit trail, under the rules for personal data |
| Retention, and sweeping files with no row | A crash between a file reaching the disk and its row being saved or removed, or a removal that fails, leaves a file behind. Decide how long files stay, and clear them on a schedule |

### Excel

`app/core/excel.py` writes a list with XlsxWriter's `constant_memory`, so a row goes to disk as it arrives, and the route
reads the database in blocks with `ListView.everything`. A file exports exactly the address's filters and order.

```python
columns = (ExcelColumn(_("Code")), ExcelColumn(_("Cost"), "number"), ExcelColumn(_("Next inspection"), "date"))
return excel_response(_("Equipment"), columns, rows, settings.time_zone)
```

| What | How |
|---|---|
| Numbers | Rounded by the application's rule, half up, to the column's decimals, because Excel keeps 15 significant digits. A value still too long goes as right-aligned text, every digit there |
| Dates and moments | Real date cells in Excel's own short format, so they read as the computer that opens the file writes them. A moment is shown in the application's time zone. Excel's calendar starts in 1900, so anything earlier goes as text |
| Text | Always text, so a long code keeps its zeros. What could start a formula begins with an apostrophe: see [SEC-15](standards.md#security). A cell holds 32,767 characters: longer text is cut, ends in an ellipsis and leaves a line in the log, with the row and not the text |
| Language | Headers, the sheet's name, the file's name and labels are the person's, and the date in the file's name is the application's day |
| Too many rows | More than Excel holds is an error, never a shorter file |

The file is written to a temporary file that the system deletes when it closes, and that has no name on disk where the system allows that. The response closes it however the download ends, so a client that leaves, a send that fails or a server that stops leaves no business data behind. A background task would not: it runs only after a response that finished.

It runs in a worker thread, so other requests go on. Nobody sees progress: at 50,000 rows it takes about 2.2 seconds on one
laptop before the download starts. Progress belongs to [milestone 4](#milestones).

## Identity

The application has no login of its own. A trusted reverse proxy authenticates the person and passes who they are in
headers; the header names and the mapping from groups to roles are settings. Those headers are believed only from the
addresses in `APP_TRUSTED_PROXIES`, by default this computer. Uvicorn listens on `127.0.0.1` by default and must run
with `--no-proxy-headers`: otherwise it replaces the proxy's address with the one in `X-Forwarded-For`, and everyone
gets 401. A repeated identity header means no identity.

A visitor without identity gets the 401 page, with no navigation, version or user menu. The public paths are exactly
`/health` and `/static/`. For local work, a fake identity is available and refuses to start outside development.

## Layouts

An application chooses its arrangement in its settings. The [settings menu](#settings-menu) shows each one live.

| Setting | Options | Typical use |
|---|---|---|
| `APP_LAYOUT_NAVIGATION` | `side`, `compact` (icons only), `top`, `hidden` (opened from a button) | Side for management applications; top for a few sections |
| `APP_LAYOUT_STICKY_HEADER` | `true`, `false` | Fixed for long tables |
| `APP_LAYOUT_WIDTH` | `full`, `centered` | Full for tables; centred for forms |
| `APP_LAYOUT_DENSITY` | `normal`, `compact` | Compact for data-heavy screens |
| `APP_LAYOUT_THEME_CONTROL` | `dropdown`, `toggle`, `swap`, `radio` | How the header's theme control looks |
| `APP_LAYOUT_LANGUAGE_CONTROL` | `dropdown`, `select`, `menu` | How the header's language control looks |
| `APP_LAYOUT_CHOICES` | A list of `navigation`, `sticky_header`, `width`, `density`, `theme_control`, `language_control`; all by default | What each person may change. What is left out stays as set above; `[]` hides the menu |

On a phone the navigation is always a panel opened from a button, and the theme and language controls move into the user
menu.

## Settings menu

`/settings` belongs to the shell, in `app/core/` and `app/ui/`, so a clone keeps it. It is reached from the user menu and
the [command palette](#command-palette), and in the demo from the sidebar too. Each choice is a form sent to
`/preferences`, which accepts only the values in `LAYOUTS`, saves them in cookies as theme and language are saved, and
sends the person back. No inline script or style is needed, and focus returns to the control that was used.

| Section | Offers |
|---|---|
| Layout | Navigation, fixed header, width, density |
| Theme and language | Theme: as the system, light, dark. Language |
| How the theme control looks | daisyUI's `theme-controller` as a dropdown, toggle, swap or radio, each live on the page |
| How the language control looks | A dropdown, a select with its own button, or a menu list, each live on the page |

The two last sections exist so that an organization can compare what daisyUI offers on real controls, then fix one with
`APP_LAYOUT_THEME_CONTROL` and `APP_LAYOUT_LANGUAGE_CONTROL` and leave it out of `APP_LAYOUT_CHOICES`. A toggle and a swap
have two states, so they cannot choose *as the system*: they show what is on screen, and the first change fixes a theme.
The select has a button because arrow keys change a closed select, and sending the form on each would change the
language under a person who is only reading the list.

## Command palette

Ctrl+K, Cmd+K or the header's search button open a native `<dialog>` with the ARIA combobox and listbox pattern: arrow
keys, Enter, Escape, focus returned, grouped results, a state for no results, by click and by touch, translated. It is
part of the shell, so every application has it, and it calls no service: `/search` gives the options, ready-made and
already filtered by role, the first time it opens, and `palette.js` filters them in the page.

It finds navigation items, the settings menu, and whatever is registered:

```python
register_search(application.state, lambda: [SearchItem(_("Invoices"), "/invoices", _("Records"), _("Sent and paid"))])
```

The function runs inside each request, so it can use the person's language. The demo registers every component this way,
with daisyUI's translated names and descriptions, and its class names as keywords.

## Components

A component is one Jinja macro or one piece of the shell, using only the brand's colours. Screens call macros, not
daisyUI classes, so the look can change in one place. Each macro appears on the page of its component in the
[gallery](#gallery), and has tests. The macros today are `icon`, `page_heading`, `message`, `button`, `link_button`, `card`,
`panel`, `stats`, `stat`, `badge`, `status_label`, `progress`, `steps`, `table`, `empty_state`, `command`, `select_field`, `item_list`,
`breadcrumbs`, `description_list`, `tabs`, `chart`, `dialog`, `dialog_buttons`, `input_field`, `field_error`,
`error_summary`, `textarea_field`, `date_field`, `number_field`, `checkbox_field`, `radio_group`, `searchable_select`,
`file_field`, `form_actions`, `confirmation`, `confirm_link`, `conflict_notice`, `grouped_table`, `dialog_action`, `filter_bar`, `list_summary`, `server_table`, `row_header`, `cell`, `row_actions`
and `pagination`.

Tabs come in two kinds. `tabs` are links, one address each, as on the equipment detail: they work without JavaScript and
with the back button, so they are a navigation with `aria-current`. The server reads what every panel needs and sends them
all, with the closed one hidden, so that paper can show both. Where panels are switched in the browser, as the gallery's
Preview and Code switch, `app.js` gives ARIA's tab pattern with its arrow keys.

Printing belongs to the shell: navigation, header and actions leave, a table's scrolling box opens, its header repeats on
each page, and a row stays whole. The page wears the light theme while it prints, because paper is white and a browser
leaves out backgrounds. The equipment detail prints both of its tabs.

## The demo

A fictional company maintains its equipment. The scenario needs no real data:

| Screen | What it exercises | Since |
|---|---|---|
| Dashboard | Stats, a table, badges, progress, steps, an empty state, formats, content replaced with focus and an announcement, and charts from the generated rows. Without those rows it keeps its fixed values and says what to run | Milestone 1 |
| Gallery | [Every component on offer](#gallery), by category, with its status, its macro and every official example | Milestone 1 |
| Administration | Visible only to one role, proving permissions | Milestone 1 |
| Equipment list, `/equipment` | Server table with 50,000 rows, search, filters, sorting, paging, row actions, its empty and no-results states, Excel export | Milestone 2 |
| Equipment detail, `/equipment/<id>` | Breadcrumbs, description list, tabs as links, history of work orders, status label, print style | Milestone 2 |
| Planning, `/planning` | Rich table: groups on the server, and one row edited at a time in a dialog | Milestone 2 |
| Work order form, `/work-orders/new` and `/work-orders/<id>/edit` | All form fields, validation, decimals, dates, file upload, delete with a confirmation | Milestone 3 |
| Import | Long task with progress, its result and its errors | Milestone 4 |

The demo's tables, `equipment` and `work_order`, with `work_order_file` for what people attach, hold what `app/demo/generate.py` makes: 50,000 pieces of equipment and
10,000 work orders, from a seed, with no third-party package. Each row comes from a hash of the seed and its position, so
the same seed gives the same rows on any computer and Python version. Work orders fall unevenly, so a detail page can
show a history of three, of two, of one, or none. Generating refuses to run outside development, because it replaces what
those tables hold.

The data tells one story, and every screen reads the same one. It ends on a fixed day, `LAST_DAY` in `app/demo/models.py`,
which is the demo's today whenever it is read, so what is overdue does not change with the calendar. Orders open from
1 January to that day. Those opened more than 60 days earlier are nearly all closed, about 96 %, and the few left open are
really late; newer ones spread across the states. Moments fall at noon at the ends of that range, so no time zone moves
one to another month. The dashboard's figures, charts and Overdue card come from these rows, Overdue leads to Planning's
own overdue filter, and `overdue()` is the one definition of the word. One fictional role exists, `admin`.

A first run stays `cp .env.example .env` and one command, with no database to prepare. Generating is one more command,
in seconds, and it can run while the server does. A screen that reads the rows asks first, in `app/demo/data.py`: if the
SQLite file is not there it does not connect, so showing a page never creates one. Without the rows, or with migrations
behind the code, it shows the command to run, and with a database that does not answer it says so. Every other
screen keeps working.

## Gallery

There is one gallery, at `/gallery`: every free daisyUI component, live and in the current theme, so a person can see what
is available and ask for it by name.

| Page | Shows |
|---|---|
| `/gallery` | Each component as a card with a small live example, by category, with its status and a live filter |
| `/gallery/<name>` | Name, description, status and note, our macro where there is one, the class table by group, then every official example with a Preview and Code switch and a copy button. Previous and next component, and on wide screens an index of the page |

| Status | Meaning |
|---|---|
| Approved | Our macro, tests and a review. This is what applications should use. Today: `alert`, `button` and `card` |
| Available | An official example, shown as published, not audited by us. It is not a promise of accessibility |
| Decorative | Not meant for management applications |
| Not recommended | Fails a standard, or has a better option in this base; its note states why |

A macro can exist before its component is approved: `badge`, `progress`, `stat`, `steps` and `table` have tests and are on
the dashboard, and wait for a person's review.

`app/ui/catalog.py` is the one list. It survives deleting the demo, and it feeds the gallery, the documentation and
`catalog.json`.

### Where the examples come from

Nothing in the gallery is written by hand, so a new daisyUI version updates it by itself. daisyUI's documentation pages,
at the version's git tag, hold 68 components and 590 `html` examples, and daisyUI publishes translations of them.
`tools/vendor.py` collects them into `tools/tailwind/daisyui-docs.json`, pinned in `vendor.json` at daisyUI's own version.
`tools/gallery.py` turns that file into `app/demo/examples/`: for each component its title, description, class tables and
every example, with the Spanish and Catalan daisyUI publishes, and daisyUI's MIT notice beside them. `tools/gallery.py
check` fails if that folder is out of date.

daisyUI translates nearly all descriptions and most class descriptions, but only a few example titles. Text it leaves in
English stays in English, marked with `lang="en"`. Text inside an example is left as published, as is its language.

`transform`, in `tools/gallery.py`, is the only place an example changes, and always so that it runs under the Content
Security Policy, which is not weakened for it:

| In the official example | In the gallery |
|---|---|
| `$$`, a placeholder for a class prefix | Removed |
| An image on another server | A local neutral placeholder under `app/ui/static/placeholders/`, keeping its size and classes |
| `style="..."`, or a `<style>` inside an SVG | `data-style`, applied by `app.js` through the CSSOM |
| `onclick="x.showModal()"`, `x.close()` | `data-dialog`, `data-dialog-close`, handled by `app.js` |
| A repeated id, radio group or anchor name on a page | A new name, with `for`, `popovertarget`, `aria-*`, links and calls in step |
| A `<script>` | Shown as code with a note, not run. Its text keeps the address it was published with |
| The year its documentation computes in place | `YYYY` |

The Code tab shows, and the copy button copies, the transformed code: what ran is what a person gets, and it works here.
What is fixed to the screen (dock, FAB, toast, drawer, a modal without `<dialog>`) stays inside its preview box, because
the box contains layout. A native `<dialog>` or popover opens in the browser's top layer, over the page, as a modal should.

Tailwind's own colours are [removed from this base](decisions.md), so an example that uses them, such as
`checked:bg-blue-200`, shows the theme's colour instead, and says so. Theme names other than `light` and `dark` are not in
the stylesheet, so `theme-controller` examples for them do nothing visible.

The generator stops rather than guess, and the update then holds daisyUI back:

| Case | Why it needs a person |
|---|---|
| A page with no frontmatter, title, description or class table, or a line it cannot read | The format changed |
| An example heading with no `html` block, a block with no heading, or two under one heading | The format changed |
| A documentation page with no place in `app/ui/catalog.py` | Its status is a decision |
| An inline handler other than `showModal` and `close`, an address on another server that is not an image, or a `<style>` it cannot move | It would break the policy |

## Documentation for assistants

An assistant should load only what it needs. The pages below come from daisyUI's `llms.txt` and are a reference for
assistants; the [gallery](#gallery)'s examples come from daisyUI's documentation source. `tools/components.py` cuts
`llms.txt`, about 20,000 tokens, into one page per component of about 375 tokens on average, counting 4 characters per token, each with OKF-style
frontmatter. Nothing is interpreted: the file is cut at its headings, and a test fails if a page drifts from it.

| File | Read |
|---|---|
| `docs/components/README.md` | First: what exists, with its status and use |
| `docs/components/rules.md` | Once: how classes and colours are used |
| `docs/components/<name>.md` | Only for the components in use |
| `docs/components/catalog.json` | The same list, for programs |

daisyui.com serves only the latest `llms.txt`, so `tools/vendor.py` rebuilds it from the files at the version's git tag,
the way the site builds it. For the pinned version, the result is identical to the site's file. If the site's build file
changes, the hash in `vendor.json` refuses the rebuild until a person has compared the two.

The generator stops rather than guesses, in each of these cases:

| Case | Why it needs a person |
|---|---|
| A component in the official file but not in `app/ui/catalog.py` | Its status is a decision |
| A generated page whose component left the official file | It is stale |
| A hand-written page on an official name | Generating would overwrite it |
| A catalogue entry with no official section and no page of its own | There is nothing to read |
| A page with no description, or an official section with no description or documentation link | The index would be empty, or the format changed. A description may be plain or quoted YAML |

Where daisyUI's text disagrees with this repository, such as its advice to use a CDN or `npm`, this repository wins, and
each page says so.

## Adapting it

| To do this | Change |
|---|---|
| Your colours, radius and logos | The base uses daisyUI's `light` and `dark` themes as they come. To change them, paste what [daisyUI's theme generator](https://daisyui.com/theme-generator/) gives you into `app/brand/theme.css`, in hex or oklch, and run `tools/css.py`. Contrast of your theme's text colours is then computed |
| Another CSS library | `app/ui/`: the macros and the stylesheet's source; screens do not change |
| Your languages | Each folder under `locales/` is a required language: add yours, run `tools/translations.py update` and translate it. Change `APP_LANGUAGES` too |
| Your time zone | `APP_TIME_ZONE`; the default is UTC |
| Your database | `APP_DATABASE_URL`, then `alembic upgrade head`. See [Data](#data) |
| Your uploads | `APP_UPLOAD_FOLDER`, `APP_UPLOAD_MAX_BYTES`, `APP_REQUEST_MAX_BYTES`, and `KINDS` in `app/core/uploads.py`. Read [what production needs](#uploads) |
| Add a table | A model on `Base`, its module imported in `migrations/env.py`, then `alembic revision --autogenerate` and read what it wrote. A test compares models and migrations |
| Your identity proxy | Settings: `APP_TRUSTED_PROXIES`, `APP_HEADER_*`, `APP_GROUPS_SEPARATOR`, `APP_ROLE_GROUPS` |
| Start an application | Clone your copy and run `tools/remove_demo.py`, then `tools/css.py`. It deletes the demo with its tests and icons, its models and first migration, the gallery's source and placeholders, renames `demo-admins` in `.env.example`, and turns the rules only the demo proved to *By hand*. The application keeps the settings menu, the palette, `app/core/`'s database and Alembic with no migrations, ready for its own, and its stylesheet shrinks by more than a quarter. Run it before adding a migration, which would otherwise follow the demo's. `tools/gallery.py` stays, with nothing to do |
| Add your own component | A macro in `app/ui/`, its line in `app/ui/catalog.py`, and a page in `docs/components/`. Only `description` is required in the page's frontmatter; do not put the `Generated by tools/components.py` marker in it. `tools/components.py` keeps your page and adds it to the index. An approved component needs `macro=` in its line. In your organization's base, add `app/demo/templates/demo/gallery/specimens/<name>.html` and it appears on its gallery page; applications have no gallery |
| Fix or hide the settings menu | `APP_LAYOUT_*` for the look, `APP_LAYOUT_CHOICES` for what people may change; `[]` hides the menu |
| Add to the search | `register_search`, as [the palette](#command-palette) shows |

An application that needs something different changes it: the code belongs to whoever cloned it. There is no update
mechanism. When the base improves, an application compares versions and takes what it wants.

`AGENTS.md`, the documentation and the checks travel with every clone. Any of them can be removed and the application
still runs.
