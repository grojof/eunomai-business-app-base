# Checks

| Check | What it proves |
|---|---|
| A new module | `tests/test_new_module.py` reads what `tools/new_module.py` writes and every refusal. `tests/demo/test_new_module.py` runs it in an organization's template, with a field of every type, translates the texts as a person would, and runs that application's whole suite once, browser checks included, with `tools/test.py` as a person's computer runs it and with its start page reading the new table. That one run also proves the template and the demo's removal: each once ran the same suite on its own |
| Unit and integration tests | Behaviour, including permissions per role |
| Tests with `app/demo/` deleted | In a copy without the demo, the stylesheet builds and every tool check passes; the tests pass, browser tests included, in the run of *A new module*, as a person runs them: nothing is set for it, and no test may stay out because the demo has gone. These tests live in `tests/demo/`: they go with the demo, as does everything else that only makes sense while it exists |
| An organization's template | A fictional layer makes one: nothing of the demo or of the base's workflows, its languages alone, its name, both themes and its font in the stylesheet, the font served under the policy, its own tests passing (in the run of *A new module*), the same files from a second run, and a layer that reaches beyond its place refused before anything is written |
| Accessibility scan, in both themes | No automatically detectable failure on real screens: the start, error, settings and administration pages, every layout, each look of the theme and language controls, the open palette, the equipment list and its detail, the dashboard with charts and an open data table, planning with the editor open, the work order form empty, filled, with errors, with files and with a conflict, its confirmations as a page and in a dialog, the searchable select with its list open, the gallery's index and the frame of its pages; the page's title in the top bar in every navigation mode, with the sticky header on and off; dense and wide lists; Planning's filter panel shown and hidden, wide and on a phone; the equipment page with its charts; the board; Planning's timeline; the calendar in month, week, agenda and after its "+ more", in three languages. Official examples are left out: see [Standards](standards.md#official-examples) |
| Brand contrast | Each text colour of a theme added to `theme.css` against its background |
| Keyboard tests | Sorting, paging and changing tab keep focus, the table's box scrolls, and the editor opens, keeps the keyboard and gives focus back. Every control of the start page is reached with visible focus; focus stops clear of the sticky header; Escape closes the user menu, the phone menu, a dialog and the palette, and returns focus; each look of the theme and language controls, the Preview and Code switch and the copy button work with a keyboard. A list's own choices and the filter panel's button keep focus; a chart's table filters its list; a card moves by its form with focus following it; the timeline's box scrolls; an event is reached and moved through its form |
| Tab order | The Tab key visits the visible controls in the order of the page, on the start page and on a page full of controls |
| Language checks | See [Standards](standards.md#how-language-is-checked) |
| Screens without JavaScript | A real browser with JavaScript off sorts, filters and pages the list, changes tab and reaches the editor, and creates, refuses, saves and deletes a work order, with a file and with a conflict. It changes a list's choices, opens and hides the filter panel, follows a chart's links, moves a card, switches to the timeline, and moves through the calendar's agenda |
| Views at their limits | A card dragged by a pointer and by a finger, an event dragged across time zones, each bar of a timeline beside its row at a larger text and a compact density, each view at 320 pixels with longer texts and at 640, which is 1280 at 200 % zoom |
| Uploads | A test for each refusal, on the checks alone and through the route. A real server refuses a body it has not read, and real Chrome was tried by hand past both limits |
| Two people | The window between reading and writing is forced in a test, so the database's own check is what answers, and two real browsers meet the conflict |
| Exports | Each file is unzipped and read as XML: order, rows, cell types, rounding and neutralised text |
| Database tests | The [data rules](standards.md#data), the lists and the screens on generated rows: on SQLite on every system, and on PostgreSQL in the Ubuntu job, with `TEST_DATABASE_URL` set. Each test gets a schema of its own, so nothing in that database is touched. On GitHub Actions on Linux an empty `TEST_DATABASE_URL` fails the run, so a job cannot pass on SQLite by accident; the Dependencies job, which has no database, says so with `TESTS_ON_SQLITE_ALONE`. The whole suite runs on a computer before merging, with `tools/test.py` and `TEST_DATABASE_URL`, on both; GitHub runs Ubuntu, with both databases, when started by hand and for each dependency update: start it before publishing, and after a change to the database layer |
| Running them | `tools/test.py` runs every test in parallel (pytest-xdist, as many at a time as the cores and the free memory allow, up to eight: each worker starts its own browser, server and database, and one per core ran the computer out of memory), at a low priority, so the person's own programs come first, then, alone and at the normal priority, those marked `serial`: a test that measures or waits on the clock is marked by the conftest from what it calls, so a new one is too. An idle worker takes tests from a busy one, and a test marked `long` starts first, one at the head of each worker's share, so none is left waiting for it at the end. It ends with one line that counts both passes, which a connector reads; pytest's own options go after `--`. `--affected` runs only what the files changed against main can break, by fixed rules it prints; anything it does not know runs everything. `--application` leaves out, in both passes, the tests marked `base`, which prove the base's own machinery (the shell, the macros, the data helpers, the tools; the list is in `tests/conftest.py`): an application's `[tests]` uses it, so a person's computer runs what the application can break, about a fifth of the time. It does so only while the base is as the template left it, by the fingerprints and package versions in `tests/base_files.json`: an application that changed a file of the base, as its documentation allows for its own components, or a package version the base's tests proved, runs every test, and the runner says why. Plain `pytest` still runs one test at a time |
| Scans in both themes | A scan opens the page in the light theme, then switches it to the dark one as the theme control does, with no reload, and scans again: one load instead of two. The colours change at once, with no easing, because the scan measures the page at rest. A test proves, on the pages with the most kinds of content and charts, that the switched page paints wherever the scan looks as the page loaded dark. The settings page shows which theme is chosen, so its scans load each |
| Rule tracing | Every rule has a source and a check. Tests are read from pytest's collection, so a comment or a string cannot pass as one, and no *Automatic* rule lacks its test |
| Invented values | No invented colours or sizes in templates, including `[color:#ff0000]`, and Tailwind's palette removed |
| Invented classes | Every class in use generates CSS, as [COMP-04](standards.md#components) says |
| Generated stylesheet | `tools/css.py check`: `app.css` matches the templates |
| Component pages | `tools/components.py check`: `docs/base/components/` matches the official file and the catalogue |
| Gallery data | `tools/gallery.py check`: `app/demo/examples/` matches daisyUI's documentation. A browser opens every component page and fails on console errors, policy violations and failed requests. Every official example appears, counted from the source; no inline style, handler or other server reaches a page; ids are unique per page |
| Copied files | `tools/vendor.py check`: each file matches its recorded hash, and Lucide's folder holds exactly the pinned version's files |
| Icons and illustrations | `tools/icons.py check` and `tests/test_icons.py`: every name asked for exists, nothing is drawn inline, the organization's icons look like Lucide's and share no name with them, and every SVG shown as an image holds nothing that runs or loads. A browser test plays animated illustrations under the policy |
| Linter, type checker, lock file, [dependency rules](dependencies.md#dependencies) | The code and its dependencies |

Browser tests use Playwright for Python and a vendored axe-core. Both are development tools: no server needs them.
